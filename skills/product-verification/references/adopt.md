# Adopt verification in an existing product

1. Read the repo entry point and canonical context. Inspect current scripts, tests, CI, browser recipes, release rules, and flow maps. Check the working tree and recent source before editing. Name the primary user surface and one critical journey with its prerequisites and observable result.
2. Run the existing startup and checks. Diagnose a broken baseline before documenting it as a recipe. Identify the smallest missing capability: perhaps a reliable start/doctor command, one driver, a flow entry, or an evidence location. Reuse the repo's tooling and package manager; add no dependency without a concrete need.
3. Put durable, source-grounded instructions in the repo's existing verification location. If none exists, add one thin repo-local entry point and a small feature map, starting with the top 3–5 journeys. Each entry should say how a user reaches it, how to drive it, what result proves success, prerequisites, and unsafe/external effects. Load one entry at a time. Do not add a second backlog or force a universal memory layout.
4. Make the driver repeatable and bounded: a read-only doctor/plan; isolated ports, data, and browser state when needed; deterministic launch, readiness, drive, and cleanup; stable selectors or commands; useful failure output; and small sanitized evidence bound to revision and dirty-tree state. Never kill a process merely by name. A dry-run label does not prove absence of side effects.
5. Execute the documented instructions from a fresh agent's perspective: launch, doctor, drive one mapped journey through the real surface, observe the result and any side effects, retain evidence, and clean up only what this run created. Fix the recipe if the run fails. Record which other journeys and external layers remain unproven.

If a new repo already has a starter with a verification contract, follow that starter's README. For an existing repo, port only the missing ideas after checking compatibility; do not replace a working verification interface.
